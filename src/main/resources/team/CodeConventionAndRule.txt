3. 패키지별 역할 및 세부 규칙



3-1. controller

- 클라이언트의 요청을 전달받고 적절한 Service를 호출한다.

- 비즈니스 로직을 Controller 내부에 작성하지 않는다.

- 일반 페이지(Thymeleaf) 요청을 처리하는 `Controller`와 REST API 요청을 처리하는 `RestController`를 목적에 맞게 분리한다.

- 요청 데이터는 Request DTO로 필수로 전달받으며, 응답 데이터는 Response DTO를 사용한다.



3-2. service

- 비즈니스 로직을 담당하며 Controller와 Repository 사이의 데이터 흐름을 관리한다.

- 데이터 검증, 비즈니스 규칙 및 트랜잭션 처리를 담당한다.



3-3. repository

- 데이터베이스 접근을 담당하는 패키지이다.

- Spring Data JPA 기반 인터페이스와 MyBatis 기반 리포지토리를 명확히 구분하여 관리한다.



3-4. entity (또는 repository.entitiy)

- 데이터베이스 테이블과 매핑되는 JPA Entity 객체를 관리한다.

- 상태나 유형을 표현할 때는 단순한 `boolean` 대신 `Enum` 클래스를 적극 활용한다.

- Entity는 API 요청 및 응답 객체로 직접 사용하지 않고 DTO를 분리하여 활용한다.



3-5. dto

- 계층 간 데이터 전달을 목적으로 사용하며 Request와 Response를 명확히 구분한다.

- 요청 DTO: `기능명 + Request` (예: `AddFoodRequest`)

- 응답 DTO: `기능명 + Response` (예: `FoodResponse`)



3-6. exception (개인 수정 엄금)

- 프로젝트 전반에서 발생하는 예외를 관리하는 패키지이다.

- 사용자 정의 예외 클래스 및 공통 예외 처리 클래스를 배치하여 각 도메인에서 중복 구현을 방지한다.



3-7. templates (Resources)

- 화면 뷰(Thymeleaf HTML) 파일은 기능/도메인 폴더(`disposal`, `ingredient`, `inventory`, `order` 등)로 분류하여 관리한다.

- 공통으로 사용되는 네비게이션바, 사이드바, 모달 등의 조각 파일은 `fragment` 디렉터리에 모아 관리한다.





4. 명명 규칙 (Naming Convention)



4-1. 클래스 및 패키지 명명 규칙

- 클래스명: 첫 글자 대문자, 이후 카멜 케이스 (예: `FoodController`)

- 인터페이스명: 첫 글자 대문자, 이후 카멜 케이스 (예: `FoodRepository`)

- 메서드명: 첫 글자 소문자, 이후 카멜 케이스 (예: `addFood()`)

- 변수명: 첫 글자 소문자, 이후 카멜 케이스 (예: `foodName`)

- 패키지명: 모두 소문자 (예: `controller`, `service`)

- Enum 클래스명: 첫 글자 대문자, 이후 카멜 케이스 (예: `FoodProcessingType`)

- Enum 상수: 모두 대문자, 단어 구분은 언더바(_) (예: `PROCESSED`)



4-2. 메서드 명명 규칙 (기능별 표준 동사)

- 등록: `add` (예: `addFood()`)

- 수정: `update` (예: `updateFood()`)

- 삭제: `delete` (예: `deleteFood()`)

- 조회: `get` (예: `getFood()`)





5. Repository 작성 규칙 (JPA & MyBatis 병행)



5-1. 명명 규칙

- JPA: `JPA + 도메인명 + Repository` (예: `JPAFoodRepository`)

- MyBatis: `Mybatis + 도메인명 + Repository` (예: `MFoodRepository`)



5-2. 기술 사용 기준

- JPA: 기본적인 INSERT, UPDATE, DELETE 및 단순한 SELECT, Entity 단건/목록 조회

- MyBatis: 복잡한 JOIN, 다중 테이블 조회, GROUP BY 및 통계/집계 데이터 조회





6. 공통 코드 및 설정 파일 수정 규칙

다음 항목은 프로젝트 전체에 영향을 주는 공통 영역이므로 개인 판단으로 임의 수정하지 않는다.

1. Entity 클래스: 필드 추가/삭제 및 컬럼 변경 시 반드시 팀원과 사전 협의한다.

2. 프로젝트 설정 파일 (`pom.xml`, `application.yml` 등): 의존성 및 환경 설정에 영향을 주므로 팀원 공유 후 수정한다.

3. Exception 공통 클래스: 공통 예외 처리를 임의로 변경하거나 중복 생성하지 않는다.
