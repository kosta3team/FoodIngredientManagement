# FoodIngredientManagement 프로젝트 코드 컨벤션

## 1. 기본 개발 규칙

본 문서는 팀 프로젝트의 코드 일관성 및 유지보수성을 확보하기 위한 공통 개발 규칙이다.

- 디렉터리 및 패키지 구조는 `DirectoryHierarchical.txt`를 참고한다.
- 팀원은 새로운 클래스 및 기능을 작성할 때 본 문서의 규칙을 준수한다.
- 기존 구조나 공통 코드의 변경이 필요한 경우 임의로 수정하지 않고 팀원에게 먼저 공유한다.

---

## 2. 명명 규칙 (Naming Convention)

### 2-1. 클래스 및 패키지

| 구분 | 작성 규칙 | 예시 |
|---|---|---|
| 클래스명 | 첫 글자 대문자, 이후 카멜 케이스 | `FoodController` |
| 인터페이스명 | 첫 글자 대문자, 이후 카멜 케이스 | `FoodRepository` |
| 메서드명 | 첫 글자 소문자, 이후 카멜 케이스 | `addFood()` |
| 변수명 | 첫 글자 소문자, 이후 카멜 케이스 | `foodName` |
| 패키지명 | 모두 소문자 | `food.controller` |
| Enum 클래스명 | 첫 글자 대문자, 이후 카멜 케이스 | `FoodProcessingType` |
| Enum 상수 | 모두 대문자, 단어 구분은 언더바(_) | `PROCESSED` |

### 2-2. 메서드 명명 규칙

Controller 및 Service의 메서드는 기능의 목적을 명확하게 표현한다.

| 기능 | 명명 규칙 | 예시 |
|---|---|---|
| 등록 | `add` | `addFood()` |
| 수정 | `update` | `updateFood()` |
| 삭제 | `delete` | `deleteFood()` |
| 조회 | `get` | `getFood()` |
- 메서드명은 실제 수행하는 기능을 기준으로 작성한다.
- 위 규칙에 해당하지 않는 기능은 요구사항과 가장 유사한 동사를 사용한다.
- 동일한 기능은 도메인 간에도 가능한 한 동일한 명명 규칙을 사용한다.

## 3. Repository 작성 규칙

프로젝트에서는 JPA와 MyBatis를 함께 사용하므로 Repository 작성 시 기술을 명확하게 구분한다.

### 3-1. Repository 클래스 및 인터페이스 명명

Repository 이름 앞에 사용 기술을 명시한다.

| 구분 | 명명 규칙 | 예시 |
|---|---|---|
| JPA | `JPA + 도메인명 + Repository` | `JPAFoodRepository` |
| MyBatis | `Mybatis + 도메인명 + Repository` | `MybatisFoodRepository` |

예시 디렉터리 구조:

```text
food
└── repository
    ├── JPAFoodRepository
    └── MybatisFoodRepository
```

### 3-2. 기술 사용 기준

**JPA**
- 기본적인 INSERT, UPDATE, DELETE
- 단순한 SELECT 및 Entity 조회

**MyBatis**
- 복잡한 JOIN 및 다중 테이블 조회
- GROUP BY, 집계 함수 및 통계 데이터 조회
- 여러 테이블의 데이터를 조합하는 조회 기능

## 4. Entity 및 Enum 작성 규칙

### 4-1. Entity 작성 규칙

- Entity 클래스는 데이터베이스 테이블과 매핑되는 객체로 사용한다.
- Entity는 임의로 수정하지 않는다.
- 기존 Entity의 필드 추가, 삭제, 타입 변경 및 컬럼 변경이 필요한 경우 반드시 팀원에게 먼저 공유하고 협의한다.
- Entity를 API 요청 및 응답 객체로 직접 사용하지 않고 DTO를 활용한다.

### 4-2. Boolean 대신 Enum 사용

상태나 유형을 표현하는 필드에 단순한 `boolean`을 사용하지 않는다.

가능하면 Enum을 사용하여 상태의 의미를 명확하게 표현한다.

**잘못된 예시**

```java
private boolean processedFood;
```

**권장 예시**

```java
private FoodProcessingType processedFood;
```

Enum 클래스 예시:

```java
public enum FoodProcessingType {
    PROCESSED,
    UNPROCESSED
}
```

- Enum 상수는 모두 대문자로 작성한다.
- 여러 단어를 사용하는 경우 언더바(`_`)로 구분한다.
- JPA에서 Enum을 저장할 때는 `@Enumerated(EnumType.STRING)`을 사용한다.
- Enum은 가능한 한 실제 업무 의미를 나타내는 이름으로 작성한다.

## 5. Controller 및 Service 작성 규칙

### 5-1. Controller

- Controller는 클라이언트의 요청을 전달받고 적절한 Service를 호출한다.
- 비즈니스 로직을 Controller 내부에 작성하지 않는다.
- 요청 데이터는 Request DTO로 전달받는다.(필수)
- 응답 데이터는 Response DTO를 사용한다.(선택)
- 일반 페이지 요청과 REST API 요청은 목적에 따라 구분한다.

### 5-2. Service

- Service는 비즈니스 로직을 담당한다.
- Controller와 Repository 사이에서 데이터 처리 흐름을 관리한다.
- 데이터 검증, 비즈니스 규칙 및 트랜잭션 처리를 담당한다.
- 데이터베이스 접근이 필요한 경우 Repository를 통해 처리한다.

---

## 6. DTO 작성 규칙

DTO는 계층 간 데이터 전달을 목적으로 사용하며 Request와 Response를 구분한다.

### 6-1. 클래스 명명 규칙

| 구분 | 명명 규칙 | 예시 |
|---|---|---|
| 요청 DTO | `기능명 + Request` | `AddFoodRequest` |
| 응답 DTO | `기능명 + Response` | `FoodResponse` |

### 6-2. 디렉터리 구조

```text
food
└── dto
    ├── request
    │   ├── AddFoodRequest
    │   └── UpdateFoodNameRequest
    │
    └── response
        └── FoodResponse
```

### 6-3. 작성 기준

- Request DTO는 클라이언트로부터 전달받는 데이터를 관리한다.
- Response DTO는 클라이언트에게 반환할 데이터를 관리한다.
- DTO는 Entity와 분리하여 작성한다.
- 요청 및 응답 목적에 맞는 필드만 포함한다.
- DTO 클래스명은 반드시 `Request` 또는 `Response`로 끝나도록 작성한다.

## 7. 공통 코드 및 설정 파일 수정 규칙

다음 항목은 프로젝트 전체에 영향을 주는 공통 영역이므로 개인 판단으로 임의 수정하지 않는다.

### 7-1. Entity 클래스

- 기존 Entity의 필드 및 컬럼을 임의로 수정하지 않는다.
- 수정이 필요한 경우 팀원에게 먼저 공유하고 협의한다.
- 협의된 변경 사항을 반영한다.

### 7-2. 프로젝트 설정 파일

다음 파일은 개인적으로 임의 수정하지 않는다.

- `pom.xml`
- `application.yml` 또는 `application.yaml`

수정이 필요한 경우:
1. 수정 목적과 내용을 팀원에게 먼저 공유한다.
2. 의존성 및 환경 설정에 미치는 영향을 확인한다.
3. 팀원과 협의한 후 수정한다.

### 7-3. Exception

- 공통 Exception 및 예외 처리 클래스를 임의로 생성하거나 수정하지 않는다.
- 새로운 예외 클래스가 필요한 경우 팀원에게 먼저 공유한다.
- 기존 예외 처리 구조를 우선 확인하고 중복 구현을 방지한다.
